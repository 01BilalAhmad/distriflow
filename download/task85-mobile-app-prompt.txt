# BUILD TASK: "DistriFlow Booker" — Fully Offline-First Mobile App for FMCG Order Bookers

You are building a production-grade **offline-first mobile app** for field order bookers (salesmen) of an FMCG distribution company. The backend (REST APIs + admin website) is **already live and complete** — you only build the mobile app that talks to it. The booker works all day in areas with **zero internet**: he punches orders, records cash recoveries, and tags brand-new shops. Everything must work fully offline, be stored **locally on the phone**, and be uploaded **only when the booker manually presses Sync Up**.

---

## 1. MISSION

Build a mobile app (Android-first) named **"DistriFlow Booker"** that lets an order booker:

1. **Log in** once (online), then work the whole day **fully offline**
2. **Sync Down** (manual) — download today's shops, products, and settings to the device
3. Create **orders (bills)** offline — with **mandatory GPS capture**
4. Record **recoveries** (cash/cheque/bank) offline
5. **Tag brand-new shops** offline — with the shop's **GPS location captured automatically and mandatorily**
6. **Sync Up** (manual) — upload all locally-saved orders, recoveries, and new shops to the server
7. See which of his tagged shops are still **PENDING admin approval**

---

## 2. HARD RULES (NON-NEGOTIABLE — these come directly from the business owner)

| # | Rule |
|---|------|
| R1 | **100% offline-first.** Every core action (order, recovery, new shop tag) MUST succeed with airplane mode ON. Never block any core action because of no internet. |
| R2 | **All data lives on the phone** until manually synced. Orders, recoveries, and new-shop records are saved to local storage (SQLite) the moment the booker taps Save — never queued in memory only. |
| R3 | **NO AUTO-SYNC. EVER.** No interval timer, no connectivity-change listener, no background refresh. Data goes to the server ONLY when the booker taps **Sync Up**, and comes down ONLY when he taps **Sync Down**. If you add any automatic network call for data sync, the requirement is FAILED. |
| R4 | **Sidebar has exactly two sync options:** "Sync Up (Upload)" and "Sync Down (Download)", each showing pending counts and last-sync timestamps. |
| R5 | **GPS is mandatory** for: (a) every order, (b) every new shop tag. Without a successful GPS fix, the Save button stays disabled and a retry button is shown. |
| R6 | **New shops start as PENDING.** A tagged shop is NOT usable as a normal approved shop until the admin approves it on the website. The app shows such shops with a "PENDING — admin approval ka intezar" badge. (The server already hides pending shops' bills from admin lists — the app only needs to label them.) |
| R7 | **Idempotent sync.** Every offline record gets a `clientRef` (UUID v4) generated at creation time. Retries reuse the SAME `clientRef`. The server deduplicates on it, so double-tapping Sync Up never creates duplicates. |
| R8 | **Crash-safe.** If the app is force-killed or the phone dies mid-day, all queued data must survive app restart. Queue is persisted in SQLite, not memory. |

## 4. LOCAL DATA ARCHITECTURE (device storage)

Use **SQLite** (or the platform equivalent) with these logical tables. This mirrors the proven web implementation — keep the same shapes so behaviour matches exactly.

### 4.1 Tables

```sql
-- logged-in user (persisted session)
CREATE TABLE session ( id TEXT PRIMARY KEY, user_json TEXT NOT NULL );

-- last successful Sync Down bundle
CREATE TABLE snapshot (
  user_id   TEXT PRIMARY KEY,
  date      TEXT NOT NULL,        -- YYYY-MM-DD when downloaded
  shops_json     TEXT NOT NULL,   -- Shop[]   (APPROVED shops)
  products_json  TEXT NOT NULL,   -- Product[]
  settings_json  TEXT NOT NULL,   -- { fridayOff, unplannedEnabled }
  pending_shops_json TEXT NOT NULL-- PendingShop[] (awaiting approval)
);

-- the outbox: every offline record waiting for Sync Up
CREATE TABLE outbox (
  id         TEXT PRIMARY KEY,    -- 'loc_' + timestamp + random suffix
  kind       TEXT NOT NULL,       -- 'NEW_SHOP' | 'ORDER' | 'RECOVERY'
  label      TEXT NOT NULL,       -- human readable, e.g. "Barkat Store — Rs 12,000" / "Nayi Shop — Ali Store"
  created_at TEXT NOT NULL,       -- ISO timestamp
  url        TEXT NOT NULL,       -- '/api/outlets/tag' | '/api/orders' | '/api/recovery'
  method     TEXT NOT NULL,       -- 'POST'
  body       TEXT NOT NULL,       -- EXACT JSON string to send (clientRef already inside)
  tries      INTEGER DEFAULT 0,
  last_error TEXT
);

-- locally saved orders/recoveries/shops for the app's own lists (status QUEUED until synced)
CREATE TABLE records (
  local_id TEXT PRIMARY KEY, client_ref TEXT UNIQUE, kind TEXT, outlet_id TEXT,
  status TEXT,                 -- 'QUEUED' | 'SYNCED'
  amount REAL, label TEXT, created_at TEXT, payload_json TEXT
);

CREATE TABLE last_sync ( user_id TEXT PRIMARY KEY, up TEXT, down TEXT );  -- ISO timestamps or NULL
```

### 4.2 Record lifecycle

```
Booker taps Save (order / recovery / new shop)
  → generate clientRef = UUID v4 (once, at creation)
  → INSERT into records (status QUEUED) + INSERT into outbox (body = final API JSON incl. clientRef)
  → UI immediately shows the record in "today's" lists with a ⏳ QUEUED badge
After Sync Up item succeeds
  → remove from outbox, set records.status = 'SYNCED'
```

- Every list that shows today's activity (orders, recoveries, tagged shops) must combine **local records** (queued + synced-today) — the booker never loses sight of what he did offline.

## 5. SYNC PROTOCOL (manual only — implement EXACTLY this)

### 5.1 Sync Down ("Download")

```
1. GET {BASE_URL}/api/sync/down?userId={user.id}
2. 200 → overwrite snapshot tables (shops/products/settings/pendingShops). DO NOT touch outbox.
3. set last_sync.down = now()
4. Refresh UI: shops list, product catalog, PENDING badges.
5. Non-200 / network error → toast the error, change nothing.
```

### 5.2 Sync Up ("Upload")

```
1. rows = SELECT * FROM outbox ORDER BY created_at ASC   // FIFO
2. Re-order rows by kind priority: NEW_SHOP first, then ORDER, then RECOVERY.
   // WHY: an ORDER punched against a just-tagged shop must reach the server AFTER
   // that NEW_SHOP, otherwise the server 404s the outletId.
3. for each row (in that order):
     try fetch {BASE_URL}{row.url} { method: row.method, body: row.body, Content-Type: application/json }
     if 2xx:
         if response contains "duplicate": true → mark UI "pehle se sync ho chuka" (not an error)
         DELETE row from outbox; UPDATE records SET status='SYNCED' WHERE client_ref = row's clientRef
     else (4xx/5xx — validation error):
         UPDATE row SET tries+1, last_error = server error message
         KEEP row in outbox (booker may fix/delete it manually) — continue with next row
     catch (network failure):
         UPDATE row tries+1, last_error='Network error — dobara Sync Up dabayen'
         STOP the loop immediately (remaining rows stay queued)
4. if outbox now empty → last_sync.up = now()
5. Show result summary: "3 uploaded, 1 failed (error)", and the pending count badge.
```

### 5.3 What is FORBIDDEN

- ❌ No `setInterval` sync loop
- ❌ No `NetInfo`/`navigator.onLine`/connectivity listener that triggers sync
- ❌ No background task / work manager / push-triggered sync
- ✅ Sync happens ONLY inside the two button handlers (plus: if the user taps Sync Up while fully offline, it fails gracefully and the queue remains intact)

### 5.4 clientRef rules

- Generated **once** at creation time on the device (UUID v4), stored inside the outbox body.
- Retries (second tap of Sync Up, or app restart) reuse the SAME clientRef → server responds with `duplicate: true` and no new server record is created. This is what makes repeated Sync Up taps 100% safe.

## 7. BUSINESS RULES SUMMARY (enforce client-side; server re-validates)

1. GPS required: order (always, `fromBooker:true`), new shop tag (always). No fix → no save.
2. Friday OFF (`settings.fridayOff` + Friday): planned shops blocked from ordering; unplanned path only if `settings.unplannedEnabled`; PENDING tagged shops bypass route gates (GPS still required).
3. Recovery: `amount > 0`; CHEQUE/BANK need `reference`.
4. Order: ≥1 item; discount PERCENT ≤ 100, FLAT > 0; qty in cartons (`ctn`) and/or pieces (`pcs`) — carton × unitsPerCarton + pcs = total pieces × tradePrice = line total (estimate).
5. New shop: name/address/ownerName/ownerPhone + GPS required; channel from the fixed 4-value list; CNIC/NTN optional.
6. PENDING shop: orderable, but flagged; its orders stay invisible in admin lists until approval (server-side — nothing for the app to do except the badge).

## 8. EDGE CASES YOU MUST HANDLE

1. **Offline tap on Sync Up/Down** → friendly toast ("Internet nahi — data phone par mehfooz hai, baad mein Sync Up karein"), queue untouched.
2. **Force-kill / battery pull mid-day** → reopen app: snapshot + outbox + records all intact (SQLite).
3. **Double-tap Sync Up** → duplicate: true handling, no duplicates.
4. **Sync Up with a queued ORDER whose NEW_SHOP was never uploaded** (e.g. booker deleted the NEW_SHOP row manually) → server 404 "Outlet not found" → show last_error on the order row, keep both.
5. **GPS permission denied** → explain, offer Settings shortcut + Retry; never save without GPS.
6. **Snapshot from a previous day** → still usable for browsing, but Home's "Aaj ki Route" recomputes from `visitDays` with today's date; suggest fresh Sync Down.
7. **Product unavailable (available = 0)** → visible but qty input blocked with "Stock nahi hai".
8. **Logout** → keep snapshot? NO — clear session + snapshot; keep outbox with a warning ("Pehle Sync Up karein — warna N entries delete ho jayengi") and only clear after confirm.
9. **Clock/date** → use device local date for recovery `date`; never UTC.
10. **Large catalog** → product search must be indexed/local-instant (SQLite LIKE on name+sku+brand).
